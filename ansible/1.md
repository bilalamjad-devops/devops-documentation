# Setting Up Ansible: How I Connected One Master Server to Manage Three Hosts (Beginner-Friendly Guide)

*A hands-on walkthrough of Ansible inventory, SSH key setup, and running your first commands — no fluff, just the steps that actually work.*

---

## Introduction

If you've ever managed more than two or three servers by hand — SSHing into each one, running the same update, checking uptime, repeating the same commands over and over — you already know the pain that Ansible was built to solve.

I recently set up a small Ansible lab: **one master server controlling three host servers**, all connected securely over SSH. In this article, I'll walk you through exactly how I did it — the concepts, the commands, and the small mistakes that are easy to make the first time. By the end, you'll be able to spin up your own mini Ansible environment and run commands across multiple servers at once.

---

## The Problem

Managing infrastructure manually doesn't scale. Even with just 3–5 servers, you run into real issues:

- Logging into each server individually is slow and repetitive.
- Running the same command on every server, one by one, is error-prone.
- There's no single source of truth for *which* servers you're managing or *how* to connect to them.
- Configuration drifts over time because updates aren't applied consistently everywhere.

This is exactly the gap **configuration management tools** like Ansible fill.

---

## The Solution: Ansible

Ansible lets you control multiple remote servers **from one central machine**, using simple, human-readable files instead of manual SSH sessions. It's agentless — meaning you don't need to install any special software on the servers you're managing, just SSH access.

Three concepts make this possible:

### 🔹 Inventory
A file that lists the servers Ansible should manage, along with their connection details.

```ini
[servers]
server1 ansible_host=public_ip_1
server2 ansible_host=public_ip_2
server3 ansible_host=public_ip_3

[all:vars]
ansible_python_interpreter=/usr/bin/python3
```

### 🔹 Playbook
A YAML file describing *what* should happen on those servers — like installing a web server or updating a config file.

### 🔹 Module
The smallest building block — a single reusable action, like "install Nginx," "start Docker," or "create a file." Playbooks are essentially built out of modules.

Together: **Inventory tells Ansible *where*, Modules define *what*, and Playbooks tie it all together.**

## Step-by-Step: Building the Lab

Here's the exact setup I used — one master server, three hosts.

### Step 1: Install Ansible on the Master Server

```bash
sudo apt update
sudo apt install ansible -y
```

This is the only machine that needs Ansible installed. The hosts don't need anything special beyond SSH access and Python.

### Step 2: Set Up SSH Keys

On the master server, create a private key file that will be used to authenticate with the hosts:

```bash
cd ~/.ssh
vim ansible_key
# Paste your private key here
# Press ESC, then type :wq! to save and exit
pwd  # confirms you're in /home/ubuntu/.ssh
```

### Step 3: Test the Connection Manually

Before automating anything, confirm you can actually reach a host:

```bash
sudo ssh -i ~/.ssh/ansible_key ubuntu@<public_ip>
```

If this works, you've got a secure shell session open on the remote server. Exit back to the master with:

```bash
exit
```

### Step 4: Create Your Inventory File

If `/etc/ansible/hosts` doesn't exist (or you'd rather keep things self-contained), create your own inventory file:

```bash
mkdir ~/ansible
cd ~/ansible
vim hosts
```

Add your servers:

```ini
[servers]
server1 ansible_host=<public_ip_1>
server2 ansible_host=<public_ip_2>
server3 ansible_host=<public_ip_3>

[all:vars]
ansible_python_interpreter=/usr/bin/python3
```

Save with `ESC` then `:wq`.

### Step 5: Lock Down Permissions

SSH is strict about key file permissions — get this wrong and connections will silently fail:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/ansible_key
```

### Step 6: Test Connectivity to All Hosts

Ping every server in the inventory at once:

```bash
ansible all -m ping -i ~/ansible/hosts --private-key=~/.ssh/ansible_key
```

If everything's configured correctly, you'll get a `SUCCESS` response from each host.

### Step 7: Run Real Commands Across All Servers

Check memory usage on every host in one shot:

```bash
ansible all -a "free -h" -i ~/ansible/hosts --private-key=~/.ssh/ansible_key
```

Check uptime the same way:

```bash
ansible all -a "uptime" -i ~/ansible/hosts --private-key=~/.ssh/ansible_key
```

This is the moment it clicks — one command, three servers, one output.

## Conclusion

That's it — a working Ansible setup with one master controlling three hosts, all through secure SSH connections. To recap the core building blocks:

- **Inventory** → defines *which* servers Ansible manages
- **Playbook** → defines *what* tasks to run
- **Modules** → the actual actions that get performed
- **SSH** → the secure channel that makes it all possible

This is a small lab, but it's the same foundation used to manage fleets of hundreds of servers in production. Once you're comfortable pinging and running ad-hoc commands, the natural next step is writing your first playbook to automate a real task — like installing and configuring Nginx across all your hosts.
